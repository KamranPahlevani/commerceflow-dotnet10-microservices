## 1. هدف جلسه

در این جلسه، Repository اولیه‌ی `CommerceFlow` از یک ساختار Bootstrap ساده به یک Baseline استاندارد برای توسعه‌ی چندین Project در یک Solution تبدیل می‌شود.

تمرکز اصلی روی سه موضوع است:

1. استانداردسازی تنظیمات مشترک Projectها با `Directory.Build.props`
2. مدیریت مرکزی نسخه‌ی NuGet Packageها با `Directory.Packages.props`
3. ایجاد اولین Production Project و اولین Unit Test Project با یک Dependency Graph شفاف

هدف این است که در جلسات بعدی، با افزایش تعداد Projectها، تنظیمات Build و نسخه‌ی Packageها در فایل‌های متعدد تکرار نشوند.

# 3. Repository-wide Build Policy

## 3.1. مسئله‌ی تکرار Configuration

بدون یک Policy مرکزی، هر Project ممکن است تنظیمات مشابهی را داخل فایل `.csproj` خودش تکرار کند:

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <Nullable>enable</Nullable>
  <ImplicitUsings>enable</ImplicitUsings>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>
```

اگر Repository ده‌ها Project داشته باشد، این تکرار دو مشکل ایجاد می‌کند:

- نگهداری تنظیمات سخت‌تر می‌شود.
- احتمال `Configuration Drift` بالا می‌رود.

منظور از `Configuration Drift` این است که Projectهای مختلف به مرور Configurationهای متفاوتی پیدا کنند، بدون اینکه این تفاوت حاصل یک تصمیم معماری آگاهانه باشد.

---

## 3.2. فایل `Directory.Build.props`

فایل زیر در Root Repository قرار می‌گیرد:

```text
Directory.Build.props
```

محتوای Baseline این جلسه:

```xml
<Project>

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>

</Project>
```

این فایل Policyهای مشترک Build را برای Projectهای زیرمجموعه‌ی Repository تعریف می‌کند.

# 4. تحلیل Propertyهای مرکزی Build

## 4.1. `TargetFramework`

```xml
<TargetFramework>net10.0</TargetFramework>
```

این Property مشخص می‌کند Projectهای Repository برای چه Target Frameworkای Build شوند.

در این دوره Baseline اصلی:

```text
net10.0
```

است.

به‌جای تکرار این مقدار در هر فایل `.csproj`، آن را در `Directory.Build.props` تعریف می‌کنیم.

---

## 4.2. `Nullable`

```xml
<Nullable>enable</Nullable>
```

این گزینه `Nullable Reference Types` را فعال می‌کند.

مثال:

```csharp
string name;
```

در این حالت انتظار داریم `name` مقدار `null` نداشته باشد.

در مقابل:

```csharp
string? name;
```

صراحتاً اعلام می‌کند که `null` یک مقدار معتبر است.

هدف اصلی این قابلیت، انتقال بخشی از خطاهای مرتبط با `null` از Runtime به Compile Time است.

مثال:

```csharp
string? customerName = GetCustomerName();

int length = customerName.Length;
```

Compiler می‌تواند درباره‌ی Dereference احتمالی مقدار `null` هشدار بدهد.

---

## 4.3. `ImplicitUsings`

```xml
<ImplicitUsings>enable</ImplicitUsings>
```

در Projectهای مدرن .NET، SDK می‌تواند Namespaceهای رایج را به‌صورت ضمنی Import کند.

برای مثال، در بسیاری از Projectها نیازی نیست همیشه این موارد تکرار شوند:

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;
```

اما Namespaceهای اختصاصی Solution همچنان به‌صورت صریح Import می‌شوند.

برای مثال:

```csharp
using CommerceFlow.Catalog.Domain.Products;
```

---

## 4.4. `TreatWarningsAsErrors`

```xml
<TreatWarningsAsErrors>true</TreatWarningsAsErrors>
```

این Policy باعث می‌شود Warningهای Build با سخت‌گیری بیشتری مدیریت شوند.

هدف مطلوب Repository:

```text
0 Warning
0 Error
```

است.

فایده‌ی این Policy این است که Warningها به مرور در Codebase انباشته نمی‌شوند و Developer مجبور می‌شود قبل از Merge شدن تغییرات، علت Warning را بررسی کند.

# 6. `Directory.Build.targets`

فایل زیر یکی دیگر از مکانیزم‌های مهم `MSBuild` است:

```text
Directory.Build.targets
```

اما در این جلسه آن را ایجاد نمی‌کنیم.

این فایل زمانی مفید است که یک `Custom Target` واقعی برای فرآیند Build داشته باشیم؛ برای مثال:

```text
BeforeBuild
AfterBuild
Custom Validation
Code Generation
```

در Baseline فعلی چنین نیازی وجود ندارد.

اصل معماری:

> `No speculative infrastructure`

یعنی Infrastructure صرفاً به این دلیل که ممکن است در آینده لازم شود، ایجاد نمی‌شود.

# 7. Central Package Management

## 7.1. مسئله‌ی Package Version Drift

در Repository بزرگ، ممکن است چند Project از یک NuGet Package مشترک استفاده کنند.

مدل پراکنده:

```xml
<PackageReference Include="Some.Package" Version="5.0.0" />
```

اگر همین Version در چندین فایل `.csproj` تکرار شود، Update کردن Package می‌تواند نیازمند تغییر فایل‌های متعدد باشد.

همچنین ممکن است Versionها ناخواسته متفاوت شوند:

```text
Project A → 5.0.0
Project B → 5.0.0
Project C → 5.1.0
Project D → 5.0.0
```

این وضعیت را می‌توان `Package Version Drift` در نظر گرفت.

---

## 7.2. فایل `Directory.Packages.props`

برای مدیریت مرکزی Versionهای NuGet از فایل زیر استفاده می‌کنیم:

```text
Directory.Packages.props
```

Baseline نهایی این جلسه:

```xml
<Project>

  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="coverlet.collector" Version="6.0.4" />
    <PackageVersion Include="Microsoft.NET.Test.Sdk" Version="17.14.1" />
    <PackageVersion Include="xunit" Version="2.9.3" />
    <PackageVersion Include="xunit.runner.visualstudio" Version="3.1.4" />
  </ItemGroup>

</Project>
```

---

## 7.3. `ManagePackageVersionsCentrally`

```xml
<ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
```

با فعال بودن این Property، Version Packageها می‌تواند در `Directory.Packages.props` تعریف شود و فایل `.csproj` صرفاً Dependency را Declare کند.

مثال:

### Version Policy

در `Directory.Packages.props`:

```xml
<PackageVersion Include="xunit" Version="2.9.3" />
```

### Dependency Declaration

در فایل `.csproj`:

```xml
<PackageReference Include="xunit" />
```

در نتیجه:

```text
PackageVersion
      ↓
Repository-level Version Policy
```

و:

```text
PackageReference
      ↓
Project-level Dependency Declaration
```

# 8. تفاوت `PackageReference` و `PackageVersion`

## `PackageVersion`

محل تعریف Version مرکزی:

```xml
<PackageVersion Include="xunit" Version="2.9.3" />
```

مسئولیت:

```text
Version Governance
```

## `PackageReference`

اعلام Dependency در Project:

```xml
<PackageReference Include="xunit" />
```

مسئولیت:

```text
Dependency Declaration
```

این Separation باعث می‌شود فایل `.csproj` بگوید Project به چه چیزی وابسته است، بدون اینکه Policy نسخه‌ی کل Repository را در خودش نگهداری کند.

# 13. Monorepo و Microservices

در این دوره چند Service داخل یک Git Repository نگهداری می‌شوند.

این مدل:

```text

```

نام دارد.

قرار گرفتن چند Service در یک Repository به این معنی نیست که همه‌ی آن‌ها یک Runtime یا Deployment واحد هستند.

```text
Runtime Process

Message Contract
Independent Evolution
```

نه صرفاً با تعداد Git Repositoryها.

```xml

```

این Item باعث می‌شود Namespace مربوط به `Xunit` در Project به‌صورت Global Using در دسترس باشد.

```csharp
}
```

بدون اینکه در هر فایل الزاماً این خط تکرار شود:

```csharp
using Xunit;
```

# 35. اصول معماری و Repository Engineering این جلسه

## `Convention over Duplication`

Policy مشترک یک بار در Root تعریف می‌شود و در Projectها تکرار نمی‌شود.

## `Centralized Policy`

Versionهای NuGet و تنظیمات مشترک Build مالک مرکزی دارند.

## `No speculative infrastructure`

فایلی مانند `Directory.Build.targets` تا زمانی که Use Case واقعی نداشته باشد ایجاد نمی‌شود.

## `No template garbage`

فایل‌هایی مانند `Class1.cs` یا Test نمونه‌ی بدون Business Value در Commit نهایی باقی نمی‌مانند.

## `Explicit dependency direction`

Dependency بین Projectها باید جهت معماری مشخص داشته باشد.

## `Minimal project files`

فایل `.csproj` فقط Configuration و Dependencyهای خاص همان Project را نگهداری می‌کند.
